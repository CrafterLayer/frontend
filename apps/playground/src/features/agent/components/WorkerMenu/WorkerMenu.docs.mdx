# WorkerMenu

The composer's workers chip (compact composer, 2026-10-12): a glyph and the count, opening the same
two-line radio menu as Mode, Model and Effort, where each of one, three or six section writers says
what it costs. One main coordinator still applies validated sections in page order.

<Canvas of={Stories.Balanced} />

## Usage and API

Use in the Agent composer when the host forwards the selection into the real build engine. Do not
treat it as a model picker, a promise of better accuracy, or permission to run several mutating
edits against the same page or file.

| Prop       | Type                                | Meaning                                              |
| ---------- | ----------------------------------- | ---------------------------------------------------- |
| `locale`   | `'en' \| 'ar'`                      | Label, options and build-only hint.                  |
| `value`    | `BuildWorkerCount` (`1 \| 3 \| 6`)  | Controlled choice owned by the host/controller.      |
| `running`  | `boolean`                           | Keeps the count during the current run, and says so. |
| `onChange` | `(count: BuildWorkerCount) => void` | Emits only allowed numeric limits.                   |

```tsx
<WorkerMenu locale={locale} value={workers} running={run !== null} onChange={setWorkers} />
```

Stories cover default three workers, sequential work, six workers, disabled during a run, and narrow
RTL dark chrome. This component does not start tasks or alter an active pool.

## Accessibility and layout

The chip is ChoiceMenu's trigger: named by the whole ("Build workers: 3 workers"), with the count as
its visible word and the glyph beside it, so a narrow panel can show it beside Send. The menu keeps
the platform's keyboard map (Enter, Space and the arrows open it; Esc returns focus). While a
request runs the menu still opens, its tooltip says the count is fixed, and a pick changes nothing:
the controller keeps the count the build started with. Logical spacing, editor tokens and a 44px
coarse-pointer target keep it compact and RTL-safe.

Larger limits may consume more provider concurrency and cost; speed and output quality must be
measured separately. The host must capture the chosen limit for each run.
